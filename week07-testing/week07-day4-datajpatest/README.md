## 💡 What I Learned Today

### 1. @DataJpaTest vs @WebMvcTest vs @SpringBootTest

| | `@WebMvcTest` (Day 3) | `@DataJpaTest` (Day 4) | `@SpringBootTest` |
|---|---|---|---|
| What loads | Web layer only | JPA layer only (entities, repositories) | Full app context |
| Database | Not loaded | Embedded, in-memory (H2 by default) | Real or mocked |
| Speed | ~1 second | ~1–2 seconds | 3–10 seconds |
| Use for | Controller / HTTP contract tests | Repository / query tests | Integration tests |
| Transactional | N/A | Yes — rolled back after each test | Configurable |

### 2. TestEntityManager vs the Repository

`TestEntityManager` is a test-only helper around JPA's `EntityManager`. The key reason to use it for **fixture setup** instead of `taskRepository.save(...)`:

> If `TaskRepository.save()` has a bug, and you also use `save()` to set up your test data, a bug in `findByStatus()` might get masked by a bug in `save()` — or vice versa. Using `entityManager.persistAndFlush()` for setup keeps the thing being tested (the repository's query methods) isolated from the thing being used to set up the test.

```java
@Autowired
private TestEntityManager entityManager;

@Autowired
private TaskRepository taskRepository; // the thing under test

@BeforeEach
void setUp() {
    entityManager.persistAndFlush(Task.builder()
            .title("Fix login bug")
            .status(Task.Status.TODO)
            .priority(Task.Priority.HIGH)
            .ownerEmail("alice@example.com")
            .build());

    entityManager.clear(); // detach — forces the repository to actually hit the DB
}
```

### 3. Why `entityManager.clear()` matters

Without `clear()`, entities you just persisted stay in the **first-level cache** (the persistence context). A repository query might return a cached, detached-in-memory object instead of proving it can actually read from the database. Clearing forces every repository call in the test to go through real SQL.

### 4. Derived Query Methods Under Test

```java
List<Task> findByStatus(Task.Status status);
List<Task> findByStatusAndPriority(Task.Status status, Task.Priority priority);
List<Task> findByTitleContainingIgnoreCase(String keyword);
List<Task> findByDueDateBefore(LocalDate date);
long countByStatus(Task.Status status);
```

Each of these is **generated by Spring Data JPA from the method name alone** — no implementation code. The test's job is to prove the generated SQL actually does what the name implies.

### 5. Custom JPQL Query (`@Query`)

```java
@Query("SELECT t FROM Task t " +
        "WHERE t.ownerEmail = :ownerEmail AND t.status <> :status " +
        "ORDER BY t.dueDate ASC")
List<Task> findActiveTasksForOwner(@Param("ownerEmail") String ownerEmail,
                                    @Param("status") Task.Status excludedStatus);
```

JPQL queries object graphs (`Task`, `t.status`), not raw tables/columns — this is what makes it portable across databases (H2 in tests, Postgres/MySQL in production) without changing a line of query code.

## ❌ Common Mistakes

| Mistake | Fix |
|---------|-----|
| Setting up fixtures with `taskRepository.save()` | Use `TestEntityManager.persistAndFlush()` to keep setup independent of the code under test |
| Forgetting `entityManager.clear()` | Query might silently pass off the first-level cache instead of proving real SQL |
| Assuming `@DataJpaTest` uses your configured datasource | It swaps in an embedded DB automatically unless you use `@AutoConfigureTestDatabase(replace = NONE)` |
| Testing derived queries with only one row in the DB | Always seed at least one row that should be **excluded** — proves the filter, not just that the table isn't empty |
| Using `@SpringBootTest` for repository-only tests | Too slow, loads far more than needed — use `@DataJpaTest` |
| Forgetting `@PrePersist`/`@Enumerated(EnumType.STRING)` | Without `STRING`, enums persist as ordinal ints — reorder the enum later and every row silently means something else |
